## Conclusion

`02fd...` is the hardware-validated sorting + full-navigation + wake build
`c825a72e...` plus a later passive FD9 source-state diagnostic. It contains all
three confirmed fixes byte-for-byte. It is not a folder-follow fix or a release
candidate.

The ancestry is exact, not inferred from similar instruction patterns. Revert
the callback pointer instructions at file offsets `0xEADB4` and `0xEADBC` to
their `c825...` values, and zero the diagnostic cave at file offset `0x588040`
(`VA 0x988040`). The resulting full-file SHA-256 is:

```text
c825a72e1078999f74822846d35c99971f9a660addd5f12d42d50a75f0b9b80e
```

Thus the undocumented diagnostic is the only difference from the golden
sorting + traversal + wake binary.

## Recovered diagnostic behavior

The callback pointer still targets `0x988040`, but this is not the documented
`6c274509...` wrapper currently generated by
`scripts/build_folderfollow_dispatch_diag.py`.

The recovered wrapper:

- is `0x414` bytes long at `0x988040-0x988453`;
- allocates and clears a `0x1200`-byte record;
- uses magic `FFRS`, version `1`, and record size `0x1200`;
- runs only for callback arguments `a2=1, a3=1`;
- snapshots state both before and immediately after original callback
  `0x4E5FA0`;
- appends the record with `write(9, record, 0x1200)`;
- does not call `0x4E4B80` and does not destroy, build, or retarget views.

Its call graph is limited to the UTF-16 copy helper `0x41FB80`, player-context
lookup `0x459340`, current-view lookup `0x4E5680`, view count `0x438BE0`, last
matching-view lookup `0x4E57E0`, original callback `0x4E5FA0`,
`clock_gettime`, and `write`.

In addition to the explorer/current-view fields sampled by `6c274...`, it
captures previously unrecorded candidate source state directly:

| Source | Pre-record fields | Post-record fields | UTF-16 snapshots |
| --- | --- | --- | --- |
| Fixed object at `0xADD368` | pointer at `0x3C` | same fixed pointer | `+0x1654` to record `0x100` and `0x920` |
| Global pointer at `0xADD360` | pointer at `0x38`; object fields `+0x24`, `+0x230`, `+0x414`, `+0x730` at record `0x60-0x6C` | pointer at `0x9C`; fields at `0x8C-0x98` | inline `+0x28` to `0x308` / `0xB28`; string through pointer at `+0x230` to `0x510` / `0xD30` |

This aligns exactly with the next work item in `notes/status.md`: observe the

artifact therefore appears newer than the last documented experiment, not an

## Hardware run: 2026-09-14

The recovered binary was run through the installed one-shot FD9 launcher. The
test card path was:

```text
01Flat/Roots In Russia. Русский реггей 2 (2000)
02Nesteted/Slayer/Albums/Show no mercy/Evil Has No Boundaries
```

One prelude event was recorded while leaving the DAC screen and navigating
through `Music -> Files -> SD-card1`. A control Now Playing -> Folder View
gesture while the Roots track was current produced the second record. Both
records are valid `0x1200`-byte `FFRS` records with stage bits `0x37F7`.

The control record shows:

- the fixed path, source-object inline path, and matching Folder View path all
  point to Roots;
- source-object field `+0x230` is `NULL` before and after `0x4E5FA0`;
- current view, matching Folder View, explorer state, and list head/tail are
  stable immediately across the callback;
- original `0x4E5FA0` returns zero.

Playback was then advanced with physical Next, without browsing, to
`Evil Has No Boundaries` in `Show no mercy`. Before the gesture the log still
contained only the two Roots records. The return gesture reproduced the stale
Folder View: Roots remained visible, the old track was not highlighted, and
the volume wheel still responded. Immediately afterwards ADB disconnected,
the patched process exited, and the one-shot launcher rebooted the device.
After reboot the stock player was running, uptime was about 54 seconds, and the
log remained exactly 9,216 bytes. No target record reached the final
`write(9, record, 0x1200)`.

This makes `02fd...` unsuitable for another unchanged run. The failure occurs
somewhere after entry to its target wrapper but before its single final write.
Because the stale Folder View became visible, original `0x4E5FA0` probably ran;
this made one of the post-callback probes the leading suspect. In particular,
the wrapper conditionally treats source-object field `+0x230` as a UTF-16
pointer and copies through it without validating the value.

The later `eba4b0c9...` pointer-only diagnostic confirmed the cause. `+0x230`
was `NULL` in Roots and became the small scalar `0x0002EB64` while Evil Has No
Boundaries was playing. The old wrapper attempted to read a UTF-16 string from
that invalid address. Later values `0x0005BA40` and `0x000001AA` further prove
that the field is scalar state, likely cue/timing-related, not a pointer.

A safer successor should write a minimal pointer-only record first, avoid
dereferencing `+0x230`, and either use staged writes or append a second optional
string block only after the core record is durable.

That successor was built and successfully tested; see
[folderfollow-safe-pointer-diag.md](folderfollow-safe-pointer-diag.md).
